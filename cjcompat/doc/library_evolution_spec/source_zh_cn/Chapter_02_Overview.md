# 概述

## 目标和适用范围

本规范用于定义对于一个仓颉模块（仓颉的最小发布单元），在符合哪些条件的代码修改情况下，能对下游使用者提供兼容性承诺，具体分为：

1. API 兼容：改动后保证下游代码重新编译能正常完成。
2. ABI 兼容：在 API 兼容的基础上，进一步保证下游代码在不重新编译的情况可以直接重新链接。

需要注意的是，参考业界标准及实践，

1. 对于在当前模块中新增 API （注：包括新增全局变量、新增全局函数、新增自定义类型、新增扩展、已有类型新增父类和父接口、删除和放宽已有扩展中的泛型约束）导致与下游代码的符号冲突或函数重载决议失败问题，不属于 API 兼容破坏。
2. 仓颉支持 FFI 操作，新增对 foreign 函数的依赖导致与其他模块依赖的 foreign 函数的名称冲突而链接失败，不属于 ABI 兼容破坏。

本规范也同时作为 CJCOMPAT（注：仓颉工具链中提供的兼容性检查配套工具）的实现规格文档。

在参考本规范之前，希望您具有相应的仓颉语言基础知识。

特别地，

1. 由于仓颉中可以使用宏和条件编译特性，二者会导致实际参与编译的代码与源码有差别。所以本文中介绍的兼容性规则均以完成宏展开和条件编译处理后的代码为判定基准。
2. 由于仓颉支持自动类型推导，本文中涉及的类型均以自动类型推导完成后的类型结果为判定基准。
