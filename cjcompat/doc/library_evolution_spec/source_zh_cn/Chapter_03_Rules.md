# 兼容性规则

## 全局变量变更的兼容性规则

### 新增和删除场景

| 变更行为 | API 兼容性 | ABI 兼容性 |
|-|-|-|
| 新增一个全局变量 | 兼容 | 兼容 |
| 删除一个不带 public 修饰符或所在包不带 public 修饰符的全局变量 | 兼容 | 兼容 |
| 删除一个带 public 修饰符且所在包带 public 修饰符的全局变量 | 不兼容 | 不兼容 |

### 修改场景

我们称一个全局变量为**模块外可见**，当其满足以下任一条件：

1. 该全局变量带 public 修饰符且所在的包带 public 修饰符。
2. 该全局变量被其他模块外可见的声明依赖，且这些声明有 const 或 @Frozen 标记。

```cangjie
package A

// const变量x是public修饰，模块外可见，会参与下游模块的编译过程
public const x: Int64 = 10

// const变量y虽然无public修饰，模块外不可见，但也会参与下游模块的编译过程。原因在于y被foo函数依赖，而编译器当前编译期求值的实现机制
// 是将y和foo一并导出到下游包中再做计算
const y: Int64 = 10
public const func foo(): Int64 {
    return y
}

// 变量z虽然无public修饰，模块外不可见，但也会参与下游模块的编译过程。原因在于z被标记了Frozen的bar函数依赖，
// 而编译器会将bar函数体完整的导出到下游B包中，导致z会被下游模块编译依赖
let z: Int64 = 10
@Frozen
public func bar(): Int64 {
    return z
}

//==================================//

package B

import A.*

const m: Int64 = x
const n: Int64 = foo()
let k: Int64 = bar()
```

对任何模块外不可见的全局变量的修改，都满足 API + ABI 兼容，以下我们仅讨论模块外可见场景

#### 修改某个全局变量的定义内容

##### 修改编译标记部分

| 变更行为 | API 兼容性 | ABI 兼容性 |
|-|-|-|
| 新增 @Deprecated 编译标记 | 基于 @Deprecated 的参数条件，当该变量在下游模块中不可用时，不兼容；否则，兼容 | 基于 @Deprecated 的参数条件，当该变量在下游模块中不可用时，不兼容；否则，兼容 |
| 删除 @Deprecated 编译标记 | 兼容 | 兼容 |
| 修改 @Deprecated 编译标记参数条件，使该变量在下游模块中从可用变为不可用时 | 不兼容 | 不兼容 |
| 修改 @Deprecated 编译标记参数条件，使该变量在下游模块中从不可用变为可用时 | 兼容 | 兼容 |
| 修改 @Deprecated 编译标记参数条件，使该变量在下游模块中的可用性未发生改变时 | 兼容 | 兼容 |

```cangjie
/* 修改编译标记部分 -- @Deprecated */

// 场景一：给变量v1新增@Deprecated["This API will be deprecated soon"]，为API+ABI均兼容，因为下游模块仍能正常使用，仅是会产生编译告警
// 场景二：给变量v1新增@Deprecated["This API is deprecated", strict: true]，为API+ABI均不兼容，因为下游模块已不能正常使用，会产生编译报错
public let v1: Int64 = 1

// 场景三：删除变量v2上的@Deprecated标记，为API+ABI均兼容，因为下游模块可以恢复使用
@Deprecated["This API is deprecated", strict: true]
public let v2: Int32 = 1

// 场景四：修改变量v3上的@Deprecated标记为@Deprecated["This API is deprecated", strict: true]，为API+ABI均不兼容，因为下游模块变为不能正常使用
@Deprecated["This API will be deprecated soon"]
public let v3: String = "hello"
```

##### 修改修饰符部分

| 变更行为 | API 兼容性 | ABI 兼容性 |
|-|-|-|
| 访问修饰符由 public 改为非 public | 不兼容 | 不兼容 |
| 访问修饰符由非 public 改为 public | 兼容 | 兼容 |
| 访问修饰符在非 public 的其他三种情况间（protected/internal/private）变化 | 兼容 | 兼容 |
| 修改 let 修饰符为 var 修饰符 | 兼容 | 兼容 |
| 修改 var 修饰符为 let 修饰符 | 不兼容 | 不兼容 |
| 修改 let 修饰符为 const 修饰符 | 兼容 | 不兼容 |
| 修改 var 修饰符为 const 修饰符 | 不兼容 | 不兼容 |
| 修改 const 修饰符为 let 修饰符 | 不兼容 | 不兼容 |
| 修改 const 修饰符为 var 修饰符 | 不兼容 | 不兼容 |

```cangjie
/* 修改修饰符部分 -- const */

package A

// 场景一：修改变量x的修饰符为const，为API兼容，但ABI不兼容，因为改后编译A包后，x作为const变量，在做完编译期计算后，会被优化删除而不存在于最终二进制中
public let x: Int64 = 1

// 场景二：修改变量x的修饰符为const，为API+ABI均不兼容，因为改后下游B包中y在foo中的写入使用会变成非法
public var y: Int64 = 1

// 场景三：修改变量z的修饰符为let或var，为API+ABI均不兼容，因为改后下游B包中z在k中使用会变成非法
public const z: Int64 = 1

//==================================//

package B

import A.*

public let m: Int64 = x
public func foo() {
    y = 2
}
public const k: Int64 = z
```

##### 修改变量名、变量类型及初始值部分

| 变更行为 | API 兼容性 | ABI 兼容性 | 备注 |
|-|-|-|-|
| 修改变量名 | 不兼容 | 不兼容 | NA |
| 修改变量类型 A 为 B | 当 B 是 A 的子类型时，兼容；否则，不兼容 | 当 B 是 A 的子类型，且 A 和 B 均为 class 或 interface 类型时，兼容；否则，不兼容 | ABI 兼容要求“A 和 B 均为 class 或 interface 类型”的原因在于，值类型可以是某个 interface 类型的子类型，但二者内存布局不同，无法 ABI 兼容 |
| 修改非 const 变量的初始值 | 兼容 | 兼容 | NA |  
| 修改 const 变量的初始值 | 兼容 | 不兼容 | 目前编译器实现导致，被包外可见的 const 变量和函数直接或间接依赖的包外不可见的 const 变量也需要被下游代码的编译器求值使用 |

```cangjie
/* 修改变量类型部分 */

interface I {}
struct S <: I {}
class C <: I {}

// 1）若修改变量t的类型为S，则满足API兼容，但不满足ABI兼容。原因在于虽然S是I的子类型，但值类型和引用类型的内存布局不同，在ABI层面无法兼容
// 2) 若修改变量t的类型为C，则同时满足API和ABI兼容
let t: I = ...
```

```cangjie
/* 修改初始值部分 -- const变量 */

package A

// 若修改const变量x的初始值，则满足API兼容，但不满足ABI兼容。原因在于下游包B中的编译期求值结果会依然使用x的老版初始值
public const x: Int64 = 10
// 若修改const变量y的初始值，也是满足API兼容，但不满足ABI兼容。原因在于y被foo函数依赖，而编译器当前编译期求值的实现机制
// 是将y和foo一并导出到下游包中再做计算，进而导致下游包B中的编译期求值结果会依然使用y的老版初始值
const y: Int64 = 10
public const func foo(): Int64 {
    return y
}

//==================================//

package B

import A.*

const m: Int64 = x
const n: Int64 = foo()
```

## 全局函数变更的兼容性规则

### 新增和删除场景

| 变更行为 | API 兼容性 | ABI 兼容性 |
|-|-|-|
| 新增一个全局函数 | 兼容 | 兼容 |
| 删除一个不带 public 修饰符或所在包不带 public 修饰符的全局函数 | 兼容 | 兼容 |
| 删除一个带 public 修饰符且所在包带 public 修饰符的全局函数 | 不兼容 | 不兼容 |

### 修改场景

我们称一个全局函数为**模块外可见**，当其满足以下任一条件：

1. 该全局函数带 public 修饰符且所在的包带 public 修饰符。
2. 该全局函数在其他模块外可见、且标记了 const 的全局变量或静态成员变量的定义中使用。
3. 该全局函数被其他模块外可见、且标记了 const 或 @Frozen 的函数定义中使用。

```cangjie
package A

// 函数f1是public修饰，模块外可见，会参与下游模块的编译过程
public func f1(): Int64 {
    return 1
}

// 函数f2虽然无public修饰，模块外不可见，但也会参与下游模块的编译过程。原因在于f2被f3函数依赖，而编译器当前编译期求值的实现机制
// 是f3的签名和函数体一并完整导出到下游包中做计算，因此会导致f2被动的需要导出到下游包
const func f2(): Int64 {
    return 2
}
public const func f3(): Int64 {
    f2()
}

// 函数f4虽然无public修饰，模块外不可见，但也会参与下游模块的编译过程。原因在于f4被标记了Frozen的f5函数依赖，
// 而编译器会将f5函数体完整的导出到下游B包中，导致f4会被下游模块编译依赖
func f4(): Int64 {
    return 2
}
@Frozen
public const func f5(): Int64 {
    f4()
}

//==================================//

package B

import A.*

let m: Int64 = f1()
const n: Int64 = f3()
let k: Int64 = f5()
```

对任何模块外不可见的全局函数的修改，都满足 API + ABI 兼容，以下我们仅讨论模块外可见场景。

#### 修改某个全局函数的定义内容

##### 修改编译标记部分

| 变更行为 | API 兼容性 | ABI 兼容性 | 备注 |
|-|-|-|-|
| 新增 @Deprecated 编译标记 | 基于 @Deprecated 的参数条件，当该函数在下游模块中不可用时，不兼容；否则，兼容 | 基于 @Deprecated 的参数条件，当该函数在下游模块中不可用时，不兼容；否则，兼容 | NA |
| 删除 @Deprecated 编译标记 | 兼容 | 兼容 | NA |
| 修改 @Deprecated 编译标记参数条件，使该函数在下游模块中从可用变为不可用时 | 不兼容 | 不兼容 | NA |
| 修改 @Deprecated 编译标记参数条件，使该函数在下游模块中从不可用变为可用时 | 兼容 | 兼容 | NA |
| 修改 @Deprecated 编译标记参数条件，使该函数在下游模块中的可用性未发生改变时 | 兼容 | 兼容 | NA |
| 新增 @C 编译标记 | 不兼容 | 不兼容 | 新增 @C 编译标记后，下游模块使用处需要增加 unsafe，否则会编译报错；同时会影响 mangle name |
| 删除 @C 编译标记 | 兼容 | 不兼容 | 删除 @C 编译标记会影响函数的 mangle name |
| 新增、删除或修改 @CallingConv 编译标记，使被标记函数的调用约定发生变化（注：目前支持的调用约定有两种：CDECL 和 STDCALL）| 兼容 | 不兼容 | 调用约定发生变化时，参数传递机制等会发生变化，导致 ABI 不兼容 |
| 新增或删除 @CallingConv 编译标记，但被标记函数的调用约定未发生变化（注：目前支持的调用约定有两种：CDECL 和 STDCALL）| 兼容 | 兼容 | NA |
| 新增 @Frozen 编译标记 | 兼容 | 兼容 | NA |
| 删除 @Frozen 编译标记 | 兼容 | 不兼容 | ABI 不兼容的原因在于，为了保证版本 A 与 B 兼容， B 与 C 兼容，则 A 与 C 兼容的传递性 |

```cangjie
/* 修改编译标记部分 -- @C编译标记 */

package A

// 场景一：给函数foo新增@C编译标记，为API+ABI不兼容。原因在于，下游包中m中对foo的使用点会需要增加unsafe标记，否则会编译报错
public func foo(): Int64 {
    return 1
}

// 场景二：删除函数bar的@C编译标记，为API兼容，但ABI不兼容。原因在于，bar从CFunc变为普通仓颉函数后，mangle name发生变化，导致下游包无法按旧mangle name链接
@C
public func bar(): Int64 {
    return 1
}

//==================================//

package B

import A.*

let m: Int64 = foo()
let n: Int64 =  unsafe { bar() }
```

```cangjie
/* 修改编译标记部分 -- @CallingConv编译标记 */

// 场景一：给函数foo新增@CallingConv[STDCALL]，为API兼容，但ABI不兼容。原因在于，默认情况下CFunc的调用约定为CDECL，新增标记后发生了变化
// 场景二：给函数foo新增@CallingConv[CDECL]，为API+ABI兼容。原因在于，默认情况下CFunc的调用约定为CDECL，新增标记后未发生实质变化
@C
public func foo(): Int64 {
    return 1
}

// 场景三：删除函数bar的@CallingConv[STDCALL]编译标记，为API兼容，但ABI不兼容。原因在于，默认情况下CFunc的调用约定为CDECL，新增标记后发生了变化
@CallingConv[STDCALL]
@C
public func bar(): Int64 {
    return 1
}
```

```cangjie
/* 修改编译标记部分 -- @Frozen编译标记 */

package A

// 场景一：给函数foo新增@Frozen编译标记，为API+ABI均兼容
public func foo(): Int64 {
    return 1
}

// 场景二：删除函数bar的@Frozen编译标记，为API兼容，但ABI不兼容。原因在于，为了保证版本A与B兼容，B与C兼容，则A与C兼容的传递性。
// 否则，用户可以分两步进行修改，第一步删除@Frozen，第二步再修改bar函数体，从而产生实质的ABI破坏
@Frozen
public func bar(): Int64 {
    return 1
}

//==================================//

package B

import A.*

let m: Int64 = foo()
let n: Int64 = bar()
```

## struct 类型的兼容性规则

### 新增和删除场景

| 变更行为 | API 兼容性 | ABI 兼容性 |
|-|-|-|
| 新增一个 struct 类型 | 兼容 | 兼容 |
| 删除一个不带 public 修饰符或所在包不带 public 修饰符的 struct 类型 | 兼容 | 兼容 |
| 删除一个带 public 修饰符且所在包带 public 修饰符的 struct 类型 | 不兼容 | 不兼容 |

### 修改场景

struct 类型的模块外可见定义与上文所述的全局变量和函数不同。我们称一个 struct 类型为**模块外可见**，当其满足以下任一条件：

1. 该 struct 类型带 public 修饰符且所在的包带 public 修饰符。
2. 该 struct 类型被其他模块外可见的 struct/class 类型中的成员变量的类型定义中使用。
3. 该 struct 类型被其他模块外可见的声明依赖，且这些声明有 const 或 @Frozen 标记。

```cangjie
package A

// struct类型S1是public修饰，模块外可见，会参与下游模块的编译过程
public struct S1 {
    let x: Int64 = 0
}

// struct类型S2虽然无public修饰，模块外不可见，但也会参与下游模块的编译过程。原因在于S2用于定义S3中的x成员变量类型，产生依赖
struct S2 {
    let x: Int64 = 0
}
public struct S3 {
    let x: S2 = S2()
}

//==================================//

package B

import A.*

let m: S1 = S1()
let n: S3 = S3()
```
